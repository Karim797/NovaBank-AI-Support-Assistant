# NovaBank AI Support Assistant

An end-to-end AI support system for a **fictional UK digital bank**, combining intent classification, deterministic routing, grounded retrieval, refusal/escalation logic, observability, feedback collection, testing, and cloud deployment.

## Live demo

**Frontend:** https://novabank-ai-support-assistant-mrpqfixibk6uwtady5xpqf.streamlit.app/

**Backend readiness:** https://novabank-ai-support-assistant-production.up.railway.app/ready

Current deployment:

```text
Streamlit Community Cloud
        ↓
Railway FastAPI service
        ↓
Intent classifier
        ↓
Deterministic router
        ↓
Hybrid retrieval / policy path
        ↓
Grounded response + sources + escalation signal
```

> NovaBank is invented. Every policy, fee, limit, and SLA in this repository is synthetic and describes no real financial institution.

---

## What this project demonstrates

The project is designed around the parts that have to exist **around** an ML model before it can safely serve customer-facing requests:

- 77-class banking intent classification
- confidence-based routing
- deterministic safety/policy paths
- hybrid BM25 + TF-IDF retrieval
- grounded answers with source validation
- out-of-scope refusal and human escalation
- FastAPI serving layer
- Streamlit demo UI
- API-key protection and rate limiting
- structured logging and request IDs
- prediction and feedback persistence
- monitoring and drift tooling
- Docker, CI/CD, MLflow, and cloud deployment design

The LLM does not decide routing, escalation, or which evidence is allowed. Those decisions are enforced in Python.

### Routing behaviour

| Condition | Route | Behaviour |
|---|---|---|
| Confident safety/policy intent | `deterministic_policy` | Fixed response, no generation |
| Confident normal intent | `rag_topic_filtered` | Retrieval restricted by intent topic |
| Low-confidence intent | `rag_unfiltered` | Search full knowledge base |
| Retrieval below relevance floor | `no_relevant_context` | Refuse and escalate |
| Ungrounded model output | `ungrounded_answer` | Discard answer and refuse |
| Provider failure | `llm_unavailable` | Safe degraded response |

## API

| Endpoint | Purpose |
|---|---|
| `GET /health` | Liveness |
| `GET /ready` | Model/index/service readiness |
| `POST /chat` | Single assistant request |
| `POST /chat/batch` | Batch requests |

Example local request:

```bash
curl -s http://localhost:8000/chat \
  -H 'content-type: application/json' \
  -d '{"question":"Why is my cash withdrawal still pending?"}'
```

## Testing and quality gates

The test suite covers both software behaviour and ML quality.

Examples include:

- request/schema validation
- readiness vs liveness semantics
- API-key authentication
- rate limiting
- request-ID propagation
- feedback persistence
- PII-safe logging
- retrieval behaviour
- deterministic policy routing
- refusal behaviour
- grounding validation
- provider-failure degradation

Selected ML quality gates include:

| Gate | Threshold |
|---|---:|
| Macro F1 | ≥ 0.85 |
| Dedup F1 gap | < 0.01 |
| Coverage | ≥ 0.85 |
| Retrieval Recall@4 | ≥ 0.85 |
| Out-of-scope refusal | ≥ 0.75 |

The routing threshold is treated as a measured operating point, not a hard-coded guess.

## Security and reliability

Implemented controls include:

- secrets kept out of Git
- constant-time API-key comparison
- Pydantic request validation
- maximum question length
- batch-size limits
- rate limiting
- request IDs
- structured JSON logging
- card/PIN/CVV redaction before logging/answer handling
- raw questions not stored directly
- safe refusal on missing evidence
- safe degraded behaviour if the answer provider fails
- dependency/image/secret scanning in CI configuration

For a larger production system, the next security layer would be OAuth2/JWT, gateway-level rate limiting, centralized secret rotation, and a managed production database.

## Important engineering choices

1. **Deterministic routing instead of an agent**  
   Routing and escalation are auditable Python logic rather than LLM decisions.

2. **Grounding enforced in code**  
   Returned citations must belong to retrieved evidence; invalid grounding is rejected.

3. **Hybrid lexical retrieval first**  
   BM25 + TF-IDF performs strongly on the small, jargon-heavy policy corpus and is cheap and deterministic.

4. **Model artifact includes operational metadata**  
   The classifier bundle carries threshold/version/provenance information rather than storing a bare estimator only.

5. **Offline-safe answer path**  
   The extractive provider allows the complete request path to run without an external LLM dependency.

See `docs/DECISIONS.md` for additional trade-offs.

## Limitations

- The live deployment currently uses the extractive answer provider, not a hosted generative model.
- The retrieval evaluation set is intentionally small and should eventually be replaced with real production questions.
- Requests are stateless; there is no multi-turn conversation memory yet.
- SQLite is appropriate for the MVP but should move to a managed database for multi-replica production use.
- In-process metrics reset on restart.
- No formal load test has been completed yet.
- Azure/Kubernetes files are deployment references; the live deployment is Railway + Streamlit.
