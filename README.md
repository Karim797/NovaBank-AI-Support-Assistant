# NovaBank AI Support Assistant

An end-to-end AI support system for a **fictional UK digital bank**, combining intent classification, deterministic routing, grounded retrieval, refusal/escalation logic, observability, feedback collection, testing, and cloud deployment.

## Live demo

**Frontend:** https://novabank-ai-support-assistant-mrpqfixibk6uwtady5xpqf.streamlit.app/

**Backend readiness:** https://novabank-ai-support-assistant-production.up.railway.app/ready

Current deployment:

```text
Streamlit Community Cloud
        ↓
Railway FastAPI service
        ↓
Intent classifier
        ↓
Deterministic router
        ↓
Hybrid retrieval / policy path
        ↓
Grounded response + sources + escalation signal
```

> NovaBank is invented. Every policy, fee, limit, and SLA in this repository is synthetic and describes no real financial institution.

## What this project demonstrates

The project is designed around the parts that have to exist **around** an ML model before it can safely serve customer-facing requests:

- 77-class banking intent classification
- confidence-based routing
- deterministic safety/policy paths
- hybrid BM25 + TF-IDF retrieval
- grounded answers with source validation
- out-of-scope refusal and human escalation
- FastAPI serving layer
- Streamlit demo UI
- API-key protection and rate limiting
- structured logging and request IDs
- prediction and feedback persistence
- monitoring and drift tooling
- Docker, CI/CD, MLflow, and cloud deployment design

The LLM does not decide routing, escalation, or which evidence is allowed. Those decisions are enforced in Python.

### Routing behaviour

| Condition | Route | Behaviour |
|---|---|---|
| Confident safety/policy intent | `deterministic_policy` | Fixed response, no generation |
| Confident normal intent | `rag_topic_prior` | Search the full KB with a small intent-topic ranking prior |
| Low-confidence intent | `rag_unfiltered` | Search the full KB without an intent prior |
| Retrieval below relevance floor | `no_relevant_context` | Refuse and escalate |
| Ungrounded model output | `ungrounded_answer` | Discard answer and refuse |
| Provider failure | `llm_unavailable` | Safe degraded response |

The intent signal is deliberately a **soft prior, not a hard candidate filter**. A confidently wrong classifier prediction may reorder near-ties, but it cannot make the correct document impossible to retrieve.

## Measured results

All metrics below are generated by the training/evaluation pipeline in this repository and are exercised in CI.

### Intent classification

Banking77 official split: 10,003 train / 3,080 test across 77 intents.

| Metric | Result |
|---|---:|
| Test macro F1 | **0.9125** |
| Stratified bootstrap 95% CI | **0.9024–0.9218** |
| Deduplicated test macro F1 | 0.9123 |
| Test accuracy | 0.9123 |
| Confidence threshold | 0.45 |
| Coverage at threshold | 90.6% |
| Accuracy on confident traffic | **95.5%** |
| Accuracy on low-confidence traffic | 50.7% |
| Expected calibration error (10 bins) | **0.0895** |
| Artifact size / inference | 23 MB / ~3 ms |

The reliability bins show the classifier is generally **under-confident**: for example, predictions in the 0.4–0.5 confidence bin are correct about 62% of the time. Confidence is therefore useful for routing, but it should not be read as a perfectly calibrated probability.

### Retrieval

Evaluation set: **70 labelled queries** — 50 in-scope questions (including 20 realistic paraphrases) and 20 out-of-scope questions. The evaluation separates the lexical ranking ceiling from the actual production path, which also applies the classifier-derived soft topic prior and the 0.15 relevance floor.

| Metric | Result |
|---|---:|
| Recall@1, lexical ceiling | 0.740 |
| Recall@4, lexical ceiling | **0.920** |
| Recall@4 + soft topic prior, no floor | **0.940** |
| MRR@4, lexical ceiling | 0.813 |
| MRR@4 + soft topic prior, no floor | 0.880 |
| Production Recall@4, topic prior + 0.15 floor | **0.700** |
| Production MRR@4 | 0.670 |
| Paraphrase Recall@4, production path | **0.600** |
| Out-of-scope refusal, production path | **0.900 (18/20)** |

Knowledge base: **19 documents → 107 chunks**.

The gap between the 0.94 ranking ceiling and 0.70 production recall is intentional evidence of the current trade-off: the 0.15 relevance floor improves refusal behaviour but rejects some valid paraphrases. The earlier hard topic filter has been removed because a confidently wrong intent could exclude the correct document entirely. The harder evaluation makes that failure mode visible instead of hiding it behind an easy corpus-derived set.

## Testing and quality gates

The test suite covers both software behaviour and ML quality.

Examples include:

- request/schema validation
- readiness vs liveness semantics
- API-key authentication
- per-session demo rate limiting, including `/feedback`
- request-ID propagation
- feedback persistence
- PII-safe logging
- retrieval behaviour
- deterministic policy routing
- refusal behaviour
- grounding validation
- provider-failure degradation

Selected ML quality gates include:

| Gate | Threshold |
|---|---:|
| Macro F1 | ≥ 0.85 |
| Dedup F1 gap | < 0.01 |
| Coverage | ≥ 0.85 |
| Production Retrieval Recall@4 | ≥ 0.65 |
| Out-of-scope refusal | ≥ 0.70 |
| Maximum Recall@4 loss from topic prior | ≤ 0.03 |
| Harder retrieval set | ≥ 50 in-scope / 20 paraphrase / 20 OOS |

The routing threshold is treated as a measured operating point, not a hard-coded guess. Calibration/ECE and a bootstrap confidence interval are reported so the headline classifier score is not presented as a single certainty-free number.

## Security and reliability

Implemented controls include:

- secrets kept out of Git
- constant-time API-key comparison
- Pydantic request validation
- maximum question length
- batch-size limits
- per-browser-session public-demo rate limiting, with proxy/socket fallback for direct callers
- `/feedback` rate limiting as well as chat throttling
- request IDs
- structured JSON logging
- card/PIN/CVV redaction before logging/answer handling
- raw questions not stored directly
- safe refusal on missing evidence
- safe degraded behaviour if the answer provider fails
- blocking dependency audit and secret scanning in CI
- container vulnerability findings retained as a Trivy SARIF artifact for explicit triage rather than hidden by deleting SBOM metadata

The in-process limiter is a demo fairness control, not DDoS protection. For a larger production system, the next security layer would be OAuth2/JWT, gateway-level authenticated quotas/rate limiting, centralized secret rotation, and a managed production database.

## Important engineering choices

1. **Deterministic routing instead of an agent**  
   Routing and escalation are auditable Python logic rather than LLM decisions.

2. **Grounding enforced in code**  
   Returned citations must belong to retrieved evidence; invalid grounding is rejected.

3. **Hybrid lexical retrieval with a soft intent prior**  
   BM25 + TF-IDF is cheap and deterministic on the small policy corpus. Intent topics are a ranking prior, not a hard filter, so classifier errors cannot remove evidence from the candidate set.

4. **Model artifact includes operational metadata**  
   The classifier bundle carries threshold/version/provenance information rather than storing a bare estimator only.

5. **Offline-safe answer path**  
   The extractive provider allows the complete request path to run without an external LLM dependency.

See `docs/DECISIONS.md` for additional trade-offs.

## Limitations

- The live deployment currently uses the extractive answer provider, not a hosted generative model.
- The retrieval benchmark is larger and harder than the original corpus-derived set, but it is still hand-curated rather than sampled from real production traffic.
- Production-path paraphrase Recall@4 is currently 0.60 at the 0.15 relevance floor; dense retrieval, query rewriting, or a better-calibrated relevance model are candidates only if future measurements justify them.
- Requests are stateless; there is no multi-turn conversation memory yet.
- SQLite is appropriate for the MVP but should move to a managed database for multi-replica production use.
- The in-process rate limiter is not an edge/DDoS control and resets with process state.
- In-process metrics reset on restart.
- No formal load test has been completed yet.
- Azure/Kubernetes files are deployment references; the live deployment is Railway + Streamlit.

## Next production steps

- collect real usage questions for retrieval evaluation
- measure whether dense retrieval or query rewriting improves the 0.60 paraphrase recall without weakening refusal precision
- tune the relevance floor from real false-refusal / false-answer costs rather than an arbitrary target
- move feedback persistence to Postgres for multi-replica deployment
- add multi-turn query rewriting if follow-up questions become common
- connect escalation to a real human-support/ticketing workflow
- add stronger answer-quality labels from agent review
